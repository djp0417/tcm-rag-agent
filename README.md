# rag-agent-app — 中医健康科普 RAG 问答 + 体质辨识 Agent

面向中医养生咨询的**垂直领域 RAG + Multi-Agent** 智能体。通用大模型缺乏中医养生领域的专业能力，辨证用药与禁忌判断易出错、无据可查——本项目以自建权威语料（古籍与现行标准，452 万字）为知识底座，打通「问诊追问 → 检索重排 → 安全审查 → 方案生成」全链路，并把"答错代价高"的判断从 LLM 概率链路中剥离出来。

**技术栈**：Python · FastAPI · LangGraph · chromadb · bge-m3 · bge-reranker-v2-m3 · DeepSeek（Function Calling）· SQLite · MCP

### 核心亮点

- **知识底座**：32 份 / 12,053 块 / 452 万字中医语料向量库；按文件指纹与提取器版本号增量入库，扩库仅重算变更块
- **两段式检索 + 自反思**：向量粗排 16 → 交叉编码器精排 4；**复用精排分数当检索质量传感器**，低于阈值自动改写查询重检、取历史最优（口语提问精排分 0.11 → 0.62）
- **Multi-Agent 编排**：四通道前置分流 + 五角色流水线 + 三专科专家并行扇出；安全审查持一票否决权，打回重规划上限 2 次后降级输出，异常时也不会没有方案
- **安全不走概率路径**：规则库前置路由 / 零-LLM 确定性汇总 / 交付前程序化校验三层防线，危险等级五档
- **MCP 协议化出口**：把检索、体质判定、缺口识别、安全审查封装为 4 类标准工具，支持 stdio 与 HTTP 两种模式
- **工程保障**：130+ 断言的三层测试（工具逻辑 / 协议 / 部署配置）+ 12 项零 API 回归 + 42 条评估集

> ⚠️ **免责声明**：本项目用于技术演示与健康科普，输出内容不构成医疗诊断或用药建议，出现不适请及时就医。
>

## ① 体质辨识 Agent（阶段 2 核心产出）

### 为什么是「状态机 + function calling」而不是纯 Agent

体质辨识是一条**有明确终点的流程**（问完 27 题 → 算分 → 出报告）。纯交给 LLM 自由控制会出现三类问题：跳步（没答完就下结论）、复读（反复问同一题）、不可观测（出问题无法回答"它走到哪一步了"）。

所以采用**骨架确定 + 血肉自由**的混合架构：

| 层 | 职责 | 由谁实现 |
| --- | --- | --- |
| 骨架 | 阶段推进、计分、判定、进度 | **确定性代码**（`state.py` / `constitution.py`） |
| 血肉 | 口语→分值的语义映射、自然提问、组织解释 | **LLM**（function calling） |
| 约束 | 每个阶段允许调用哪些工具 | **工具可见性**（`tools.py` 的 `_STAGE_TOOLS`） |

即「**代码判定 + 语料解释**」双轨：判定结果由代码算出（可复现、可单测），调养建议由 RAG 检索生成（有据可依）。

### 状态机

```
IDLE ──begin_consultation──▶ COLLECTING ──答完最后一题──▶ SCORING
                                                          │
                                              judge_constitution
                                                          ▼
                                        REPORTING ──用户继续追问──▶ FOLLOWUP
```

状态序列化进 SQLite（表 `consult_state`），**服务重启后问诊进度不丢**——用户答到第 18 题去吃饭，回来还能接着答。

### 六个工具与阶段可见性

| 工具 | 作用 | 可见阶段 |
| --- | --- | --- |
| `begin_consultation` | 开始辨识 | **仅 IDLE** |
| `next_question` | 取下一题 | COLLECTING |
| `record_answer` | 记录当前题（口语→1~5 分） | COLLECTING |
| `judge_constitution` | 算分并判定 | SCORING |
| `search_knowledge` | 检索知识库（自带自反思） | 全部 |
| `remember_fact` | 记长期记忆 | 全部 |
| `reset_consultation` | 清空重来 | 非 IDLE |

### 量表与判定（`constitution.py`）

依据王琦《中医体质分类与判定》（ZYYXH/T157-2009）九分法与判定公式，题目做了简化（9 种 × 3 题 = 27 题，标准版 60 题）：

```
转化分 = (原始分 − 条目数) / (条目数 × 4) × 100
偏颇体质：≥40 分「是」；30~39 分「倾向是」；<30 分「否」
平和质：  ≥60 分且其他 8 种均 <30 分「是」；≥60 分但有偏颇 ≥30 分「基本是」
```

> ⚠️ **简化版必须配的护栏：无差别作答检测**。全套选"有时"(3 分) 会得到 50 分——按标准 ≥40 即判「是」，于是八种偏颇体质**全部**被判「是」。这在数学上忠于标准（60 题版本同样如此，因为真人对症状条目不会均匀作答），但简化版条目少、用户又容易顺手全点中间档，所以加了检测：所有作答极差 ≤1 时标记 `careless`，明确告知"结论不可作为依据，请重新作答"，而不是把 8 种体质一起拍给用户。

### Agent 实测踩坑（都是提示词管不住、最后靠结构性约束解决的）

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 模型**每轮都调** `restart_consultation`，进度反复清零、永远停在第一题 | 一个工具同时承担"开始"与"重来"，描述里含"开始辨识"，模型每轮都认为该启动 | **拆成两个工具**，并让 `begin_consultation` **只在 IDLE 阶段可见** → 进入收集阶段后模型在结构上就调不到它 |
| 用户只说"我想测体质"，模型就自己把前三题**答完并记录**（编造用户答案） | 提示词写了"用户回答后再记录"也拦不住 | 双护栏：① 一轮最多记录 1 题；② **同一轮内不许"先问后记"**（`asked_turn >= turns` 则拒绝）——一道题只有在更早的轮次问出口后才允许被记录 |
| 答题进度虚高（才答 5 题显示 6/27） | `answered = sum(len(v))` 把预分配的 0 也算进去了 | 改用题目游标 `cursor` |
| 回答里泄漏 `### <next_question>` 这类工具标记 | 模型把工具名当标记吐进正文 | `_stream_clean()` 按行缓冲 + 早放行过滤（既不卡住流式、又能剔掉短标记行） |
| 同一事实被存两条长期记忆（工具存一遍、自动抽取又存一遍） | 两处入口都写记忆 + 只在原文相同时去重 | ① 模型本轮已调 `remember_fact` 就跳过自动抽取；② **向量余弦距离 ≤0.15 视为语义重复** |

**贯穿性经验**：能靠"工具可见性 / 状态约束"杜绝的错误，不要指望提示词。

## ② 三层记忆（替代"只有 6 轮"）

早期版本把"最近 6 条消息"硬编码进 prompt，几轮之后就忘了前面说过什么。根因不是模型窗口不够（DeepSeek-chat 有 64K token），而是**上下文组装策略太粗糙**。现在改为：

```
┌─ 会话记忆（**默认只属于当前会话**，新开对话即归零）──────┐
│  · 用户档案 session_profile(conv_id, key, value)      │
│    结构化 KV：年龄性别/慢病/西药/在服中药食疗/体质        │
│  · 记忆条目 memories（scope=session）：自然语言事实，      │
│    **向量召回**相关项                                  │
├─ 第 2 层 会话摘要（会话内，压缩留存）──────────────────┤
│  · 超出预算的早期对话被 LLM 压成「对话纪要」，一直携带     │
├─ 第 1 层 近期原文（会话内，滑动窗口）───────────────────┤
│  · 最近若干轮**完整原文**，保证细节不失真                 │
├─ 跨会话记忆（scope=global）**只在此刻才注入**───────────┤
│  · 仅当用户**主动问起往事**（"我上次跟你说的…"）才召回      │
└────────────────────────────────────────────────────┘
```

**预算**（字符数近似 token，中文约 1.5 字/token）：近期原文 6000 字 + 摘要 2500 字 + 召回 5 条，合计约 7~8K token，只占 64K 窗口的 1/8。

两个工程细节：
- 记忆条目入向量库时，chroma 的 **id 用数据库主键**而不是列表下标——用下标的话，删掉一条记忆后面全部前移，向量与文本就错位了（实测发现的设计缺陷）。
- 语义去重防污染：只说"我特别怕冷"两次，只会存一条。去重只用**本作用域内**条目的向量算余弦（chroma 的 `where` 过滤不了 id，只能本地算）。

### 记忆按会话隔离（2026-09-16，架构级改造）

**为什么改**：用户实测新开一个会话、只说「累、想补补」，安全卡立刻命中 6 项（附子/降压药/阿胶…），回答还复述了旧测试人设的话（"胖了十来斤""阴虚质"）。方向与直觉相反——**不是没带上下文，而是把过期上下文当成了新事实**。用户的判断没错：重新开的对话本来就不应该有记忆。

| 维度 | 隔离前 | 隔离后 |
|---|---|---|
| 档案 | `profile(key, value)` 全局共享 | `session_profile(conv_id, key, value)`，复合主键按会话切 |
| 记忆条目 | 全部跨会话 | `scope` 三态：`session`（默认）/ `global`（**只有用户明说"记住"才写**）/ `archived`（遗留，**永不注入**） |
| 时间线 | 全局共享（串档根因） | `timelines` 按 `conv_id` 隔离 |
| 删会话 | 只删消息 | 连带清 `session_profile` + session 记忆 → **删会话即完全还原** |

- 常量 `SESSION_SCOPE=0`（CLI / 无会话）、`LEGACY_SCOPE=-1`（历史归档）。旧的全局档案由 `_archive_legacy_profile()` **一次性幂等搬迁**到归档作用域：不删数据、面板可见计数、永不注入。
- **两道显式闸门**（`app/memory.py`）：`wants_recall(text)` 是窄词表（"上次 / 跟你说过 / 还记得我"），只有用户主动问起往事才召回跨会话记忆；`wants_longterm(text)`（"记住 / 记一下 / 以后都 / 帮我记"）决定新记忆写 `session` 还是 `global`。**默认永远写 session。**
- **提示词标题即语义**：注入时写「【本次对话中了解到的情况…**本次对话没提到的，一律视为「不知道」**】」——从标题上掐掉"这是这个人一贯的事实"这种误解，而不是在正文里加提醒（模型对标题的服从度高于正文）。
- 前端 API 全部带 `conv_id`（`/api/profile`、`/api/profile/panel`、`PUT/DELETE /api/profile/{key}`、`/api/memories`），文案改成"本次对话的档案"。

### 增量入库（`store/ingest_manifest.json`）

语料有 27 份 PDF、约 1GB，其中近 10 本是影印本。旧版每次 `python -m app.index`
都全量重跑——光是重新 OCR 就要几小时，还要烧掉几万次 embedding 调用，而绝大多数
文件根本没动。现在做**文件级增量**：

| 环节 | 做法 |
| --- | --- |
| 变更检测 | 每份文件记录 `(size, mtime, sha1)`。size+mtime 都一致就直接复用（**不必算 sha1**，1GB 全量哈希要好几秒）；任一不一致再算 sha1 精确比对 |
| 跳过粒度 | 未变更的文件**连文本抽取都跳过**——切块结果由「文件内容 + 流水线版本」唯一决定，文件没变则块必然相同 |
| 写库 | **按 source 精准替换**：`col.delete(where={"source": 文件名})` 后只 upsert 这批文件的块，其余文件原地不动；语料被删除时其块同步清除 |
| 块 id | 由 `chunk-{i}`（全局序号，一改就全乱）改为 `{文件哈希}-{i}`，同名文件重跑 id 不变 |
| 空跑 | 全部无变更 → 直接返回，**0 次 API 调用**（实测 1GB 语料 < 10 秒） |
| 流水线签名 | `schema/ext版本/chunk参数/embed模型/集合名` 组成指纹写进状态文件；指纹变了自动全量重建，避免"文件没变但切法变了"的脏库 |

⚠️ **代价**：改动切块或归一逻辑后必须把 `app/index.py` 的 `EXTRACTOR_VERSION` +1，
否则老块不会被更新（状态文件只会看"文件变了没"）。

**升级迁移（`adopt_existing_library`）**：给一个已经建好的库补上增量状态时，不能
简单地"状态文件不存在 → 全量重建"，那等于白扔几小时 OCR。所以第一版增量运行会
先**认领**老库：若集合里确有该 source 的块，且文件 mtime ≤ 库写入时间
（`chroma.sqlite3` 的 mtime，必须在打开库之前取），就认为库里的块就是它当前的
版本，直接登记进状态文件、块长统计从库里现算。只处理真正新增/变更的文件。

**孤儿块（库里有块、`data/` 下已无同名文件）**：默认**保留不动**——文件可能只是被
改名或挪了位置，静默丢语料比留几个脏块危险得多。确认废弃后再显式清除：

```bash
python -m app.index --prune-only   # 只清孤儿，秒级完成（推荐）
python -m app.index --prune        # 清孤儿，但挂在完整入库流程末尾（要先跑完 OCR 才轮到）
```

判定孤儿只看「`data/` 下是否存在同名文件」，**不看是否被认领**：`mtime` 晚于库写入
时间的文件只是「待重新处理」，它还在 `data/` 下，绝不能算孤儿删掉。

### 切块策略

- **结构化文档**（含 `##` 标题）：先按标题切章节（标题进 metadata），章节内再按中文句读递归切；每个 chunk 继承「书名/篇章」→ 可溯源。
- **纯文本 / OCR 结果**：直接按中文语义边界递归切（`\n\n → \n → 。！？；→ ，`）。
- `chunk_size=500 / overlap=80`：<200 语义被切碎、>800 表征被稀释；500+80 也匹配 reranker 输入长度。

### 影印本 PDF 的 OCR（`app/ocr.py`）

pypdf 只能抽文本层，扫描件/影印本是整页图片、提取结果为空。因此：

```
文字层字数 < max(200, 50 × 页数)  →  判定为图片型 PDF  →  自动降级 OCR
```

- **渲染**：`pypdfium2`（纯 pip、自带 pdfium，不需要 poppler）
- **识别**：`rapidocr_onnxruntime`（PP-OCR 模型转 ONNX，中文效果好，**不需要装 paddlepaddle**，省数百 MB）
- **断点续跑**：每识别完一页就追加写 `<hash>_<dpi>.partial.jsonl`。中途 Ctrl+C / 关电脑，下次重跑**从断点继续**。最终结果落 `<hash>_<dpi>.txt`，之后零耗时。
  > 早期版本只在整本结束时写缓存，中断一次几十页白算——实测踩出来的坑。
- **缓存键必须带页数范围**：否则调试时跑 3 页的结果会被当成全书缓存命中，正式建库静默只用前 3 页（也是实测踩到的坑）。
- **dpi 取舍**：150 dpi 快约一倍，但中医罕见字准确率下降（人名「余靖」被认成「佘靖」）；故默认 200 dpi。
- **局限**：竖排繁体古籍 OCR 质量明显低于横排简体（PP-OCR 以横排为训练主体）；OCR 结果无排版结构，只能走纯文本切块、拿不到篇章元数据。

### PDF 抽取的日志噪声（2026-09-14）

批量建库时 pypdf 会按**字体**刷 WARNING，一本影印本能刷上千行，把真正的进度信息
淹掉。两类噪声要分开处理：

| 日志 | 性质 | 处理 |
| --- | --- | --- |
| `fontTools is required to fully parse the encoding of a CFF Type1 font ...` | **真缺依赖**——字体的 CFF Type1 编码表解析不全，文本层可能缺字 | 装 `fonttools`（已列入 `requirements.txt`）；这是省不掉的 |
| `Ignoring wrong pointing object 37 0 (offset 0)` | PDF 自身 xref 指针损坏，pypdf 已容错 | 无需处理，只是吵 |

两者都走 pypdf 的 `logging`（`logging.getLogger("pypdf")`），所以除了真正装依赖，
再在 `app/index.py` 的 `configure_pdf_logging()` 里把 `pypdf` 日志级别压到 `ERROR`
（`--verbose` 原样放出），并在缺 fontTools 时**只提示一次**。

> 通用经验：排查"日志刷屏"先分清「根因告警」和「已容错的噪声」——前者装依赖解决，
> 后者压级别。只压级别会把根因一起埋掉，只装依赖则噪声仍在。

### 多编码兼容

古籍 txt 常见 GBK/Big5，直接按 utf-8 读会 `UnicodeDecodeError: byte 0xd5`。`_read_text_smart()` 做五级 fallback：`utf-8-sig → utf-8 → gb18030 → gbk → big5`，并打印识别到的编码便于排查。

## ④ 多 Agent 协作流水线（阶段 4，LangGraph）

设计稿见 `docs/阶段4-多Agent设计方案.html`，实现见 `app/multiagent/`。

### 第一层不是 Agent，是路由分流

**反模式：把每个请求都塞进 4 个 Agent。** 延迟 ×4、成本 ×4，而且错误会沿链传播
（辨证错了，后面全错）。所以最前面是分流器，只有值得深挖的请求才进流水线：

| 请求类型 | 走向 | 理由 |
|---|---|---|
| 闲聊 / 单点问答（"阳虚体质有什么表现"） | 现有单 Agent（**快路径**） | 一次检索就够，跑四条链路是浪费用户 3 倍等待 |
| 完整体质辨识后的调理方案 | **多 Agent 流水线** | 需要"辨证 → 方案 → 安全"三步推理，且要经得起审查 |
| 已识别红旗症状（"一直消瘦 / 胸口疼"） | **建议就医通道** | 直接短路——**能不出手就不出手，是医疗 Agent 的第一原则** |
| 想做方案但还没测过体质 | 引导先做辨识 | 同样是怕冷，阳虚和气郁调法完全不同，瞎猜比不猜更糟 |

分流是**两层**的：**规则层管安全**（红旗关键词先于一切，0 ms 短路且不经模型），
**LLM 管意图**（语义分流）。两者不可互换——安全不能交给概率，语义又没法用关键词穷举。

### 四个角色，每个都必须"不可替代"

> 设计原则：如果一个角色可以被别的角色顺手做完，就不要设这个角色。

| 角色 | 凭什么单独存在 |
|---|---|
| **问诊**（collector） | 唯一做量表采集的角色，产出是后续所有节点的**唯一事实源**；量表分只由它算（代码侧确定性计算） |
| **辨证**（diagnoser） | **体质 ≠ 证型**：体质是长期稳态（量表能测），证型是当前状态的病机概括（必须靠文献推理）。它承担"从数据到结论"的推理责任 |
| **方案**（planner） | 负责"把证型翻译成今天能做的事"——用户唯一真正消费的产物，也最容易越界（一不小心写成处方） |
| **安全审查**（safety） | **唯一能否决的角色**。如果它和起草者是同一个角色，就变成自证清白，独立监督的价值归零 |
| 主编（editor） | 只管表达、不产生新事实，轻量收尾（保持流式） |

### 图结构：条件边 + 否决回环

```
START → router ─┬─ fast         → fast         → END
                ├─ urgent       → urgent       → END
                ├─ need_consult → need_consult → END
                └─ pipeline     → collector → diagnoser ─┬─ planner → safety ─┬─ editor → END
                                                         └─ urgent  → END     ├─ urgent → END
                                                                              └─ planner（打回重写，最多 2 次）
                                                                                 重写用尽 → editor 降级交付
```

否决回环的出口逻辑（`route_after_safety`）：红旗优先 → 通过则主编 → 未通过且
**已重写次数 < 2** 则带 `fix_hints` 打回方案 → 用尽则降级（`degraded=True`，
只给保守建议 + 明确建议就医）。

### 共享状态（`state.py`）的两个设计要点

- **证据集中累积**（`evidence`）：所有节点检索到的块统一进池、**按内容指纹去重**。
  这样最终引用列表天然不重复，而且"引用是否真实存在"可以**程序化校验**
  （引用必须能在池里找到）——这是 Step 2 引用强校验的地基。
- **轨迹集中记录**（`trace`）：每个节点写了什么、花了多久、调了什么工具，全部留痕。
  既喂前端"思考过程"，又是链路评估的原始数据。**没有 trace 的多 Agent 是黑箱。**

### 三个必须知道的 LangGraph 坑（实现时踩到/避开）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **条件边不能改状态** | 在设计稿里写了 `after_safety` 中 `state["rewrite_count"] += 1`，照抄后**回环永远只走一次**——路由函数只做决策，它写入的字段会被框架丢弃 | 计数改由 **planner 节点自己维护**（返回 `planner_runs`），路由函数只读 |
| **累积字段没声明 reducer 会被覆盖** | 第二个节点写 `evidence` 会把第一个节点的整个盖掉，表现为"辨证检索到证据、到方案节点就没了"。**不报错，只是结果变差**，最难查 | 用 `Annotated[list, merge_evidence]` / `Annotated[list, operator.add]` |
| **两套状态会打架** | 业务状态在 `store/chat.db`，LangGraph 的 checkpointer 也想持久化 | **单一事实源**：业务事实仍以现有表为唯一真相，checkpointer 只存"本次流水线的中间态"，默认不启用 |

### 确定性安全护栏（`checks.py`）——为什么要独立于审查 Agent

审查节点是 LLM，而 LLM 有两个在安全上不可接受的性质：**不完全可控**（同一提示词偶尔放行）、
**不可复现**（temperature=0 也只是"基本确定"）。所以分两层：

- **规则层**只管"零歧义"模式，命中**直接定罪、不看模型脸色**：疗效承诺（"三天根治"）、
  疾病诊断式表述（"您患有慢性胃炎"）；
- **LLM 审查**管需要上下文的判断：证型与方案是否矛盾、引用是否挂羊头卖狗肉、红旗是否被忽略；
- 存在合法上下文的线索（**药材名、剂量**）规则只当**提示**交给 LLM——
  "忌用附子"是禁忌提醒、不是推荐，一刀切会让正常方案也被拦下（否定词守卫已实现）。

一致性约束：只要还有任何违规/红旗，`pass` 一律置 `false`——**不采信模型返回的 pass**。

### 控制流自检（`python -m app.multiagent --selftest`）

多 Agent 最怕的不是"某次答得不好"，而是**控制流悄悄坏了**：回环只走一次、
降级分支永远不进、审查被模型一句话放行……这些在真实跑批里表现为"结果偶尔怪怪的"，极难定位。
自检把 LLM 与检索换成**剧本**，只留真实的条件边与状态流，秒级跑完、100% 可复现：

| 用例 | 期望 | 验的是什么 |
|---|---|---|
| A. 方案含"附子10克 / 三天见效"，**而模型审查返回 pass=true** | 回环跑满 2 次重写 → 降级交付 | **规则层真的压住了模型**；回环计数正确 |
| B. 方案干净 | 一次通过、不进回环 | 不误触回环 |
| C. 输入"一直消瘦，胸口疼" | 0 ms 直达建议就医 | 红旗短路走的是规则层（剧本里 LLM 被换成"返回 pipeline"也没用） |

## ⑤ 安全层：独立于 RAG 的硬规则判读（阶段 5 核心产出）

### 问题：把安全结论寄托在"语料覆盖 + 模型自觉"上，是错的

实测暴露的原话（45 岁女性 / 高血压服氨氯地平 / 自服附子理中丸 / 红豆薏米茶 / 生姜红枣茶 / 桂圆 / 朋友推荐阿胶 / 疲劳畏寒大便黏）：

> 用户：这些能一起吃吗？
> 系统：资料库中没有这方面的记载。

从"不编造"看没错，从**安全**看是**失败**：附子有毒、含甘草制剂长期服用致水钠潴留升血压、
活血药叠加抗凝有出血风险——这些是**确定的药学事实**，不该因为语料没覆盖就不再提醒。

**根本原因**：安全结论走的是"检索 → LLM 判断"，而检索是概率的、LLM 也有概率漏。
凡"存在唯一正确答案、且答错代价高"的判断，都不该放在概率路径上。

### 解法：硬编码规则库 + 优先路由 + 交付前程序化兜底

```
用户输入
  │
  ├─► app/safety/scan.py  scan_text + scan_profile + merge_hits   ← 确定性，0 模型依赖
  │     命中 → 打 tag / 判 level / 交叉升级（寒湿 × 阿胶 → high）
  ├─► app/intake.py       结构化档案 / 一致性校验 / 跨轮时间线 / 信息缺口
  │
  └─► guard 区块注入 system 末尾（"优先级高于以上所有要求"）→ 再进 LLM
                                  │
                       生成完成后 app/multiagent/checks.py 程序化复检：
                       · 只引不判（引了禁忌却没说「所以对你而言」）→ 打回
                       · 硬规则判定不可用的药被当建议写入 → 直接否决（不看模型怎么说）
```

| 层 | 文件 | 职责 | 是否依赖模型 |
|---|---|---|---|
| 规则数据 | `app/safety/rules.py` | 毒性中药 / 需辨证 / 食药同源 / 西药分类 / 特殊人群，各带 tags | 否 |
| 扫描器 | `app/safety/scan.py` | 字符串+正则命中、level 判定、与档案交叉升级、元信息过滤 | 否 |
| 话术层 | `app/safety/scripts.py` | 引用必带判读 / 叫停服药 / 抗施压 / 西药排查 / 分层结论 / 典籍翻译化 | 否 |
| 接诊层 | `app/intake.py` | 年龄性别慢病西药抽取、在服清单、冲突校验、跨轮时间线、缺口追问 | 否 |
| 岗位分工 | `app/multiagent/nodes.py` | 食疗 / 经络 / 运动三专家并行扇出，主控确定性汇总 | 三专家用模型，**汇总不用** |
| 合规复检 | `app/multiagent/checks.py` | 只引不判、硬规则 × 方案冲突 | 否 |

### 几条设计判据（都是踩坑后立的规矩）

1. **规则带 tags，与档案交叉升级**。规则本身只写"什么药有什么性味"，
   危害等级由"与你是否相关"决定：阿胶单独看是"滋腻"，叠加"苔白腻/便黏"才升到 high。
2. **"在服用"要靠最近标记词判定，不能窗口内有没有**。
   反例：`朋友推荐我吃阿胶，可我自己天天喝红豆薏米茶`——"天天喝"属于薏米，
   粗窗口判断会把阿胶也标成在服用，话术从"是否适合"错升为"请暂停"。
   更糟的是它会**写进档案**并在后续每一轮复现。现在按**距离取最近**判定。
3. **"朋友推荐 / 听说 / 网上说"不算在服用**。推荐 ≠ 使用。
4. **档案必须能减**。用户说"附子理中丸我上周已经停了"，档案要摘掉它；
   否则安全提示一直在用过期的信息，用户很快就会不再相信这些提示。
   停药识别按**分句**匹配——`我停了降压药，但还在吃附子理中丸` 若按整段看会误删附子。
5. **命中即"要求"不是"建议"**。提示词里写的是"必须出现一段明确的叫停"，不是"可以考虑提醒"。
6. **只引不判要程序化检查**。把"引用之后必须紧跟『所以对你而言』"做成交付前检查，
   缺了就追加兜底句——不指望模型每轮都记得。
7. **命中分来源：本轮的展开，档案的折叠**（`annotate_origins`）。
   档案扫描是无差别的——新会话第一轮只问"累、想补补"，档案里留着的历史条目
   也会全部命中，六张判读卡糊脸，实测反馈是"突兀、答非所问"。
   现在：本轮原话命中 → 完整判读卡；档案带出且本轮没提 → LLM 侧一行带过 +
   前端折叠成「来自你档案的提醒」；本轮又提到的（含别名）→ 升回完整卡。
8. **跨会话旧话只能用「你之前提过」的口吻引用**。时间线跨会话共享，
   不加来源声明，模型会把旧会话的话当成本轮新事实复述（"你这两年胖了十来斤"）。
9. **测试不许污染跨会话状态**。档案 / 时间线 / memories 都是全局的，
   e2e 与单测跑完必须快照还原——本条就是第 7 条那次事故的根源。
10. **追问分级：阻塞项 vs 建议项**。舌象/寒热/二便缺失 → `need_more` 追问分支，
    不给方剂（`gaps`）；抗凝人群的出血倾向/支架史、女性的月经情况是
    "值得同时问"，放进 `advisory_gaps`——若把它们也当阻塞项，
    在服抗凝药却没提过出血史的用户永远走不到方案，追问就从服务变成了死锁。
    两类都缺时，`gaps` 的扫描上下文必须带**本会话时间线**（自述分散在前面几轮，
    只扫本轮会重复追问已经说过的东西）。
11. **方剂名要展开成成分再扫**。规则命中"甘草"，方案里写"参苓白术散"——
    按名字匹配什么也抓不到。`checks._FORMULA_HERBS` 白名单把常见方剂
    展开成组成药材（只展开非禁忌句里出现的），跨层一致性才不会从名字的缝里漏过去。
12. **红旗转主编，不转就医页**。safety 阶段发现红旗（慢病人群本身就是红旗词），
    原逻辑直接把三个专家跑出的方案整个丢掉、只剩一句"去就医"——
    慢病用户永远拿不到方案。正确语义：方案照常交付，就医建议由主编置顶；
    只有**路由层**红旗（便血/胸痛这类"养生咨询不该接"的输入）才走 urgent。
13. **多智能体流水线要接到 Web 上才算数**。三专家在 CLI 自检里 6/6 通过，
    但 `server.py` 没有任何引用——网页上"经络 Agent 从未输出穴位"的根因
    不是提示词，是流水线根本没被调用。`POST /api/plan/{conv_id}/chat` 把它
    变成一等公民，节点级 `step` 事件让每个 Agent 的产出实时可见。

`tools/test_architecture.py` 是 2026-09-16 第二轮新增的**架构层**回归：
验的不是"知识答得对不对"，而是**决策链路的性质**——记忆有没有归属、
安全分不分级、规则有没有替代辨证、缺口会不会追问、输出有没有契约。
全部零 API、秒级，可以进 CI。

`tools/frontend_render_check.py` 是 2026-09-16 第二轮新增的**前端**回归。
存在的理由很具体：`web/*.html` 的界面全是模板字符串拼的，Python 侧一切回归都碰不到，
于是"后端全绿、界面全错"这类问题只能在这里发现——
它抓两件事：① 模板串少个 `}`（浏览器白屏，Python 毫无察觉）；
② **字段契约漂移**，本轮就踩过：后端已把判读文本按「档位 × 用户条件」条件化
（`SafetyHit.reading`），前端却还在读 `verdict`（rules.py 里按最坏情况写死的那段），
于是血虚无湿的人问阿胶，界面仍说"不适合"——不报错、只是变差。
实现方式是把内联脚本载进 Node（极小 DOM 桩），喂一份**真实事件载荷**，断言
五档档位 / 档位依据 / 状态约束 / 挂起说明 / 换人设确认 / 引用可采信性徽章都渲染出来、
且没有退回旧 verdict。

`tools/test_precision.py` 是 2026-09-16 第三轮新增的**精度**回归（零 API，55 项）：
验的是"同一条信息换个问法、换个顺序，结论会不会变"——档位一致性、模块稳定性
（连续 5 轮齐全率）、引用可采信性、弹性、隔离确认分级、状态约束优先、药名外泄。
它与 `test_architecture` 的分工：后者验**链路性质**（有没有分级、有没有契约），
前者验**同一条链路的输出稳定性**。

`tools/e2e_safety_check.py` 是本项目最"值钱"的一个脚本：单元自检用假 LLM 验的是**图结构**，
安全规则单测只验**扫描层**，两头都对不代表串起来对——事件有没有发出来、刷新后还在不在，
只有打真服务才知道。它会校验：安全事件先于正文下发、随消息落库（刷新不丢）、
专家/追问分支正常、档案冲突被检出。跑完自动删掉测试会话。

## ⑥ 主动追问引擎（2026-09-16）

**为什么必须有**：养生咨询的输入天然是"一轮一句、慢慢挤"的——用户第一句常常只有"最近老觉得累"。
信息不全就给方案，等于**用最少的信息做最重的判断**。所以追问不是附加功能，是主干能力。

### 意图闸门：先分清"问知识"还是"求建议"

不是所有问题都该追问。用户问"阳虚有什么表现"是**知识题**，追问年龄舌象反而会把回答卡住；
用户问"我这种情况怎么调理"才是**求建议**，必须补齐信息。

```
text ──► intent_of()  ──► knowledge ──► 不追问（直接答全）
                    └──► advice    ──► followups() ──► ≤3 问
```

**踩过的坑**：「能吃阿胶吗」这类句式天生歧义——可能是"我能不能吃"，也可能是"一般人能不能吃"。
纯字面量词表会漏判，所以判据是 `_ADVICE_RES` 正则**叠加个人语境**（出现 `我/自己/本人`，
或文本命中了症状 tag）。另外 `_COMPLAINT_RE` 用的是**宽口径**词表，**没有**复用安全层的 `SYMPTOM_TAGS`——
后者服务安全分级，要求精确、宁可漏；追问要的是"感觉像在说自己不舒服就追问"，宁可多问。

### 缺口按安全边界排序（不是按问卷顺序）

`medication > chronic > age_sex > cold_heat > stool_urine > tongue > chief_time`

在服西药排第一，因为"能不能吃这个"的答案**取决于它**；年龄性别排第三，因为它改变的是鉴别方向。
最多 3 问——问多了用户直接关页面。

### 关键动作不依赖模型自觉

```python
answer, added = ensure_questions(answer, fups)   # 模型没问 → 代码补；已问够 2 条 → 不啰嗦
```

同 `checks.judgment_violations` 的思路：**"必须发生的关键动作"要有程序化兜底**。
判定"模型到底问没问"靠 `scripts.GAP_ITEMS[*].signals` 关键词匹配（不是让模型自评）。
前端拿到 `questions` 事件后渲染成**可点选的问题条**，点一下把「【在服用的药物】我的情况是：」填进输入框——
比让用户自己在正文里找"你还没告诉我…"再手打一遍顺得多。

> **与安全层的一条互斥约束**：要追问时**不给** `SG.LAYERED_CONCLUSION` 模板——
> "先给分层总括"和"信息不足不得下证型结论"是互相打架的两条，必须二选一。

### 真机验收（`tools/e2e_safety_check.py`，2026-09-16）

| 轮 | 用户输入 | 安全命中 | 追问 |
|---|---|---|---|
| 1 | 累/睡不够/便黏，是不是湿气重 | 0 项 | **3 问**（在服药物 / 慢病 / 年龄性别），且 3/3 都落在正文里 |
| 2 | 45 岁女 / 高血压 / 氨氯地平，怎么调理 | 1 项（降压药 high, stop） | 2 问（寒热 / 舌象） |
| 3 | 阿胶+薏米茶+姜枣茶+桂圆+附子理中丸 能同吃吗 | 6 项（stop） | 0 问（信息已够） |

同时验收：新会话 0 泄漏、档案为空；问诊路径 `safety` 事件先于 `memory` 下发；落库 3 条带安全判读。

## ⑦ 决策架构：六条原则与代码落点（2026-09-16 第二轮）

这一轮的输入不是"再补点知识"，而是一份**架构层诊断**：知识层已经够用，
卡住它的是"拿到信息之后怎么决策"。六条原则逐条落地如下。

### 一、记忆是「带归属的证据」，不是「无主的事实」（P0）

**事故**：同一会话里先以寒湿人设提问（苔白腻、便黏、畏寒），再以阴虚人设提问
（潮热盗汗、舌红少苔）。系统把两边硬融成"阴虚兼湿"，给出"先化湿再滋阴"——
两头不讨好；更糟的是把上一人设的用药/慢病当成"这个人的既有事实"，
整段建议建立在虚假前提上。

**改法**（`app/intake.py`）：方向冲突检测从"两对硬编码"升级为**两条互斥轴**
（寒↔热、湿↔燥）——实测的换人设路径是 **寒湿 → 湿热 → 阴虚**，
旧版第一跳能抓到、第二跳（湿热→阴虚）抓不到，因为两者同属"热"而**湿与燥相反**。

```python
_FAMILY_AXES = {"寒": (COLD,), "热": (DAMP_HEAT, YIN_DEF),
                "湿": (DAMPNESS, DAMP_HEAT), "燥": (YIN_DEF,)}
_CONFLICT_AXES = (("寒", "热"), ("湿", "燥"))
```

检出后 `cross_turn_brief` 把既往原话标成 `[往轮·待确认]`，
并强制要求先问一句「这次说的还是您本人吗」；`build_block(profile_ok=False)`
让档案带出的命中**不得以本轮事实的形态出现**。

### 二、安全是「分级」，不是「开关」（P0）

**事故**：早期"该硬不硬"（问附子能不能自己炖肉，答"不清楚，问医生"）；
后来"该软不软"（血虚证明确、无湿象，问阿胶，仍被判"不适合"）——
同一个系统两头都失手，说明问题不在"力度调多少"，而在**只有一档**。

**改法**（新增 `app/safety/tiers.py`）：四档处置，档位由「**东西 × 当前这个人的条件**」
共同决定，不由"这个东西叫什么"单独决定。

| 档位 | 触发 | 语气 |
|---|---|---|
| 明确禁止 | 毒性药材自行使用、孕产禁忌、明确冲突 | 直接叫停 + 后果 + 为什么 |
| 需专业确认 | 对证方向存在，但需舌脉/剂量/配伍判断 | 说方向 + 明确需医师定 + 不自行动手 |
| 对证但有条件 | 方向对，但有需监测的条件 | 可执行 + **停止信号** + 周期上限 |
| 可执行 | 药食同源、未命中任何禁忌条件 | 给具体做法、频次、周期 |

```python
def classify(hit, tags, gaps=None):
    if kind == "population":                 return TIER_CONFIRM
    if sub == "toxic":                       return TIER_FORBID   # 与人的条件无关
    if kind == "drug":                       return TIER_CONFIRM
    if key in _CONFIRM_FIRST:                return TIER_CONFIRM  # 活血×抗凝
    if set(hit.tags) & set(tags):            return TIER_CONDITIONAL
    if level == "high" or key in _ALWAYS_CONFIRM: return TIER_CONFIRM
    if unassessed(hit, gaps):                return TIER_CONFIRM  # 条件未评估 → 挂起
    return TIER_OK
```

### 三、规则是辨证的「约束」，不是辨证的「替代品」（P0）

**事故**：阿胶在"苔白腻、便溏、腹胀"与"舌淡苔薄白、大便正常、无湿象"两种
**完全相反**的条件下，得到同一个结论、同一套理由——等于没有辨证，
系统退化成"关键词 → 固定话术"的检索器。

**根因**：规则里的 `verdict` 是**按最坏情况写死的**（阿胶那条默认"你苔白腻、身重、便黏"）。

**改法**：判读文本改由 `tiers.render(hit)` **按条件生成**，规则里的 `verdict`
退化为兜底。检验方法（已做成回归）：**换一个相反证型问同一味药，
结论与理由都必须变、且各自绑定自己的条件**。

| 阿胶的条件 | 档位 | 结论 |
|---|---|---|
| 苔白腻、身重、便黏 | 对证但有条件 | 现在不适合，先化湿健脾，等苔腻消退再考虑 |
| 舌淡苔薄白、大便正常、无湿象 | 可执行 | 方向对得上，每日 ≤10g、饭后服、配陈皮理气，腹胀就停 |
| 什么都没说 | 需专业确认 | **结论先挂起**，取决于"有没有湿困"，先答几个问题再定 |

### 四、信息缺口触发「追问」，不触发「保守默认」（P1）

**事故（默认最危险）**：用户只是提了一句丹参，从没说自己在吃抗凝药，
回答里却冒出「华法林、阿司匹林、氯吡格雷会增加出血风险」——**吓退正确建议**。
根因：`build_block` 里只要命中项带 `anticoag` tag 就绑三件套，
而 `huoxue`（活血类）规则自身 tags 里就有 `anticoag`。

**改法**：三件套的触发闸门收紧为"**有证据**在服抗凝/抗血小板药"；
没有证据时改为 `ANTICOAG_UNKNOWN_BLOCK`——把两种情况分开说清，
然后**明确问一句**「你在不在吃阿司匹林/华法林/氯吡格雷，或放过支架吗」。
追问项 `anticoag_use` 由 `inquiry.scenario_gaps()` 动态插入到追问清单**最前**
（它决定"活血类能不能碰"，优先级最高）。

**同一原则的另一半**：`tiers.unassessed()` —— 一项药食的档位依赖某个条件，
而该条件**还没评估**时，既不放行也不警告，而是**挂起并追问**
（"我不知道你有没有湿困，所以先不说能不能吃"）。

### 五、输出有「固定契约」，不靠模型自觉（P1）

**事故**：输出模块的出现是随机的——有时有追问有时没有，有时有就医阈值有时没有，
有时有穴位有时没有。同一能力项在不同轮次得分在 0 和 9 之间跳。

**改法**（新增 `app/contract.py`）：六模块契约 + **三层保障**

```
① 分层判断（本/标）  ② 逐条结论 + 档位 + 理由  ③ 可执行（食疗/经络/起居/运动）
④ 风险管理（原处方药纪律/监测/停止信号）  ⑤ 就医与排查（含阈值）  ⑥ 缺口追问
```

1. **提示词侧**：`render_contract()` 以"必须包含"注入；
2. **程序化自检**：`audit()` 逐模块检测（宽口径关键词，宁可判"已有"）；
3. **确定性补全**：`enforce()` 用**硬规则层已有的文本**补 ——
   ② 用 `tiers.render` 的分级判读、④ 用西药的 `must_say` 原文、⑤ 用 `SCREENING` 的检查项。

两条克制：**最多补 3 段**（否则末尾堆成八股文）；**知识题一律不补**
（给"什么是阴虚"补一段"分层看：你底子偏阴液不足"是答非所问）。

### 六、知识「支撑」结论，不「生成」结论（P2）

**事故**：知识命中什么就讲什么，输出结构由检索命中率决定；
某个维度一旦检索不到就**整段消失**（穴位维度在多轮里反复缺失）。

**改法**（新增 `app/framework.py`）：`build()` 先定**判断框架**
（问题类别 → 必须覆盖的维度 → 必须排除的风险 → 尚缺的信息），
`render()` 明确要求：**某个维度在参考资料里找不到依据时，保留该维度**
并注明「此处资料库无直接依据，按通用原则处理」，**不要整段删掉**。
框架由规则生成，与检索结果**无关**——框架完整性与知识命中率解耦。

### 本轮顺带修掉的四个真缺陷

1. **否定词被当成正向命中**：中文里「没有湿气」「不怕冷」「没有放过支架」
   都会**字面命中**正向关键词。实测「阿胶补血，舌淡苔薄白，大便正常，
   **没有湿气**」被当成 `dampness` 命中 → 阿胶被判"先化湿再补"。
   已在 `tag_from_text` 加**否定词守卫**（关键词左侧 3 字内有否定词则该次命中作废，
   只要还有一处未被否定的出现，tag 仍成立）。
2. **"能不能喝"没被识别为求建议**：`_ADVICE_RES` 只有"能不能吃"。
   实测「我听说丹参泡水好，我能喝吗」既没追问、也没走安全判读。
3. **`cond_labels` 回退分支把"药自身的 tags"当成了"用户的条件"**：
   导致"条件未评估 → 挂起"这条分支永远进不去（用户什么都没说，
   阿胶照样给出"你先化湿"的判读）。属于典型的"看起来对、实际恒真"的判据。
4. **`tiers.apply_tiers` 写不回 dataclass**：`_as_dict()` 对 `SafetyHit` 返回的是
   `to_dict()` 的**新字典**，往里写字段原对象一点没变 → 分级静默失效（tier 全是空串）。
5. **后端条件化了、前端还在念旧台词**（收尾时发现）：`render()` 生成的判读文本此前
   只进提示词（模型看得到），事件与落库里的 `hit` 仍带着 rules.py 那个按最坏情况写死的
   `verdict`——于是**用户看到的和模型看到的不是同一段话**，界面永远显示"不适合你"这类
   与本人无关的通用话术。修法：`apply_tiers` 里一并预渲染 `reading`（给人看的判读正文）
   并随 `to_dict()` 下发，前端 `safetyHtml` 优先读 `reading`。
   ⚠️ 顺序有讲究：`_set(reading)` 必须在写完 `cond_labels`/`unassessed_gaps` **之后**，
   否则 `render()` 读到的还是空值，"未评估→挂起"永不生效。
   这类"字段契约漂移"不报错、只是变差，所以单独加了一条前端回归
   （`tools/frontend_render_check.py`）。

### 展示层同步（2026-09-16 第二轮收尾）

架构层的产物必须**在界面上看得见**，否则等于没做。`web/index.html` 与 `web/agent.html` 的
安全判读卡这一轮同步了五件事：

| 界面元素 | 数据来源 | 为什么必须显示 |
|---|---|---|
| 档位徽章（本轮 4 档；第三轮补出第 5 档 `不建议（无适应症）`，用中性灰，见 ⑧） | `hit.tier` + `hit.tier_label` | 风险高中低只说"东西危不危险"，档位才说"你现在该怎么处置" |
| 🔎 档位依据（你命中了：痰湿/湿困） | `hit.cond_labels` | 把结论绑回用户的具体条件，否则又变成通用话术 |
| ⏳ 结论已挂起：还差 舌象 | `hit.unassessed_gaps` | 让"缺信息 → 挂起 → 追问"对用户可见，不是黑箱 |
| 🔄 先确认一件事（前面偏寒、这次偏热；依据：本会话此前的描述） | `subject_switch` + `subject_switch_detail` | 只报一个 `true`，用户不知道依据；说清"哪一轴反了"才谈得上确认 |
| ⚖️ 所以对你而言（按档位 × 条件生成的判读正文） | `hit.reading` | 后端条件化的成果，前端不显示就白做了 |

另外三处细节：卡片底色改为**取命中里最严的那一档**（不再取 `level` 的最高值）；
头部计数从"命中 4 项"改成"明确禁止 1｜需专业确认 1｜对证但有条件 1"；
底部加一行档位说明——**同一味药换个人、换个证型结论就不同**，这句话要写在用户看得见的地方。
`subject_switch_detail` 是这一轮新加的字段（此前只下发 bool），三个路径
（`rag._safety_guard` / `agent._safety_event` / `multiagent.nodes`）同步补齐。

## ⑧ 精度与稳定性：第三轮（2026-09-16，P0-1 / P0-2 / P0-3 + P1）

### 这一轮的判断：知识层够用，问题全在「决策精度」与「输出稳定性」

第二轮把判断链路搭起来了（分级 / 框架 / 契约）；第三轮的实测反馈指向更细的一层：
**同一条信息，不同的问法、不同的顺序，系统给出的档位和口径会变。**
三条 P0 全部落成机制，判据都是"满足条件必触发"，不依赖模型自觉。

### P0-1 档位体系：唯一判定点 + 单源派生

| 症状 | 根因 | 落点 |
|---|---|---|
| 标题「对证但有条件」、正文「不能做」、指南「如果你实在想喝」三种口径打架 | 同一档位的措辞散落在多处各写各的 | `tiers.TIER_SPEC`：每档四件套（thesis / must / never / guide），`render()` 与 `tier_discipline_block()` **都从它派生** |
| 「明确禁止」与「不建议」被压成一个"不能吃" | 档位粒度缺一档 | 新增第五档 `not_needed`（不建议 / 无适应症），档位序 禁忌>确认>无适应症>有条件>可用 |
| "该软不软、该硬不硬" | 判据只看药名 | `classify()` 按 人条件 → 条件是否已评估 → 适应症 逐级判定 |

「**明确禁止 ≠ 不建议**」是这一轮的核心语义：前者是"用了有害"（方向相反 / 明文禁用），
后者是"对你没用、不必吃"。区分靠 `HerbRule` 上两个新字段——`contra`（方向相反 → 禁忌）
与 `indication`（适应症，补益类才有）。

**实测复查（真机补验时又挖出一个）**：鹿茸的 `tags` 里混着「高血压」「孕产/备孕」，
于是它们走"命中条件"分支被定成**对证但有条件**——这等于告诉一个备孕的人
"只要对证就能吃鹿茸"，而**鹿茸自己的 `not_for` 写着「高血压…禁用；孕妇禁用」**。
判据：`not_for` 写**禁用**的情形进 `contra`，写**不宜/慎用**的留在 `tags`。
全库逐条核过，命中此判据的只此一味（其余都是"不宜"，那确实是"有条件"）。

### P0-2 排查模块：规则表触发，与证型解耦

西医排查 / 经络维度**时而有时而无**——因为触发条件写死在证型分支里。
现在 `scripts.SCREEN_RULES` 是通用求值器（tags / all / any 三类条件），
`intake.screening_keys()` 遍历规则表而不是 if-else；`screening_block()` 追加
"输出前逐项核对"的硬要求。**判据是"满足条件必触发"，不是"证型对了才提"**。

### P0-3 引用层：可采信性筛选（`app/credibility.py`）

反馈原话：鹿茸条目里的「中有小白虫，入人鼻必为虫颡」被当严肃依据引进回答。
根因：引用只判"**相不相关**"，没判"**可不可采信**"。

句级三档：`ok`（药性/功效/宜忌/配伍）→ 原样；`background`（相传/传说/祝由）→
保留但标注"不得作为依据"；`reject`（鬼神致病 / 符咒祈禳 / 成仙长生 / 怪诞传闻）→ 剔除。
**整块剔除的判据**：剔完剩不下 40 字说明这块几乎全是传说，直接不喂给模型。
为什么在取用侧做而不重建索引：重建要重嵌入上万块，而一个 500 字的块里通常
只有一两句是传说，整块丢掉会把真知识一起丢掉。

> ⚠️ 幂等是个坑：注释里带"传说"二字，处理第二遍会被**再次判定**，每跑一次多补一句注释。
> 正确做法是**处理前先摘掉自己上次补的注释，并记住它存在过**——只摘不记，
> 第二遍会因为"本轮没命中传说句"而**丢注释**（改一版错一版，两个方向都踩过）。

### 顺手挖出并修掉的三个更底层的问题

**① 档案级污染：否定句被写成阳性事实（真机补验时发现，比档位问题更严重）**

实测：用户说完「**没有**高血压糖尿病」，档案变成
`慢病 ＝ 孕产/备孕、高血压、糖尿病` —— 此后每一轮卡片都印「命中：高血压」。

根因：**安全层早就有否定守卫，只有档案抽取侧没有**（`intake.extract_conditions/
extract_drugs` 用的是朴素的 `k in t`）。而档案是 CSV **只增不减**的合并，
**写错一次就错到用户删会话为止**。加两层守卫：
未否定（复用 `scan.hit_affirmative`）**且**不落在"我已经停了"的分句里
（复用 `_stop_in_clause`）——「降压药已经停了」两个方向都错过。

> **回答错只错一轮，档案错错一整个会话。**

**② `tier_basis` 没进 `to_dict()`，第三轮的核心字段一条都没下发**

`apply_tiers` 把"这一档凭什么定下来"算好写进了对象，但 `SafetyHit.to_dict()`
没带这个字段 → 前端 `h.tier_basis` 恒为 `undefined`，静默退回 `cond_labels`。
功能"看着实现了"、实际一条没下发，**不报错、只变差**。
修法：字段进 dataclass + 进 `to_dict`，并加了断言（`test_architecture` 里"档位依据进了事件载荷"）。

**③ 向量缓存键只绑位置、不绑内容，改了字会被旧向量喂回**

块 id 是 `{sha1(文件名)}-{序号}`。归一化手工表新增一个映射（`⺐`→`尤`）后，
**块数不变、id 不变** → 纯按 id 查缓存会把**上一版的旧向量**原样写进 Chroma：
库里的文字是新的、向量是旧的，检索从此静默错位。
修法：缓存键改为 `{块id}:{sha1(文字)}`；另加 `tools/rekey_embed_cache.py`
（读库重写缓存键，**0 次 embedding API**，不必为换键重嵌一万两千块）。

## ⑨ 追问环节：第四轮（2026-09-16，唯一阻塞项）

第四轮反馈的判定：三条 P0 已全部达标，**唯一待修的是追问环节**——

| 失效 | 实测 | 根因 | 修法 |
|---|---|---|---|
| ① 已知信息重复问 | "我爸爸 68 岁，有高血压和糖尿病，一直在吃药"→ 仍被问"你的年龄和性别""有没有在吃西药" | 档案抽取**正确地**剥离了亲属分句（防污染守卫），而缺口判定只看档案——被剥离的事实成了"未知" | `intake.gaps` 改**主体感知**：缺口判定走 `subject_scope`（本轮文本 + 时间线里**同一主体**的条目）；每项改 `gap_known` 宽口径证据正则。已知判定漏判的代价是重复提问，误判的代价是多问一句——所以这层刻意比档案写入守卫**宽** |
| ② 问错对象 | 咨询对象是父亲，问句全是"你的XX" | 话术模板写死"你" | `inquiry._subjectize`：主体是家人时问句切换（"（关于您父亲）他的年龄…"），`followup_block` 声明对象边界（不得用本人信息顶替） |
| ③ 该问的没问、不该问的硬贴 | 认知下降只给通用三件套；47 岁月经量少被问"放过心脏支架吗" | 清单固定模板；抗凝 advisory 只看 tag 不看证据 | `CHIEF_GAP_RULES` **主诉关联规则表**（备孕→周期排卵+药名；认知下降→药名+时间线+卒中影像+照护人），插在通用项之前；`advisory_gaps` 加**证据闸门**——确认在服抗凝/有支架史才问出血·支架两问，只聊到活血类时由阻塞项 `anticoag_use` 先问"在不在服" |

配套机制：
- **"在吃药"→"药名"升级**：说了在服药但没给药名时，追问升级为"具体哪几种"
  （`drug_names`），而不是重复问"有没有吃药"——`drug_names` 有前置闸门，
  没有在服证据的人不会被预设"你在吃药"；
- **信源守卫**："朋友推荐我吃阿胶"里的"朋友"是**信源**不是咨询对象
  （第三轮"推荐 ≠ 在服"同一陷阱在主体识别上的变体）——
  不设守卫会把本人档案整体排除、已知全部"失忆"（真机 e2e 实测翻车）；
- **换主体后"已知"同样隔离**：女儿说过的年龄/体质不得顶替爸爸的缺口
  （时间线条目按主体角色过滤）。

  （专治"用《膳食指南》'高龄衰退'论证'不是正常衰老'"式牵强引用——

## ⑫ MCP Server：把领域能力做成标准协议出口（2026-09-17）

把检索 / 安全判读 / 体质辨识 / 缺口追问**封装成标准 MCP 服务**，任何兼容 MCP 的客户端
（WorkBuddy / Claude Desktop / Cursor…）零适配接入。**不改任何现有业务逻辑**——
新增的 `app/mcp/` 全是薄包装层。

```bash
python -m app.mcp                       # stdio（本地客户端，默认）
python -m app.mcp --http --port 7863    # Streamable HTTP（第二阶段，默认只绑 127.0.0.1）
```

### 暴露的能力

| 原语 | 名称 | 说明 | 优先级 |
| --- | --- | --- | --- |
| Tool | `tcm_safety_check` | 判定药/食/保健品/西药在特定人群状态下是否可用，**返回确定性档位** | **P0** |
| Tool | `tcm_search` | 典籍检索（两段式 + 精排，过滤元信息与不可采信记载） | P0 |
| Tool | `tcm_constitution` | 九分法体质辨识（27 题 → 主体质/兼夹/调养要点） | P1 |
| Tool | `tcm_intake_gaps` | 算信息缺口并给建议追问（**上限 3 条**） | P1 |
| Resource | `tcm://kb/manifest` | 语料清单（32 份 / 12,053 块 / 构建管线） | P1 |
| Resource | `tcm://guide/scope` | **能力边界**（能答什么、不能答什么、红旗症状直接就医） | P0 |
| Resource | `tcm://session/{conv_id}/profile` | 会话档案 / 记忆 / 时间线（**只读**） | P2 |

### 五条红线（接 MCP 必须守）

1. **安全结论以结构化字段返回**（`tier` / `tier_label` / `basis`）。若只返回一段自然语言，
   客户端模型的 prompt 会把"明确禁止"柔和化成"建议谨慎"——**确定性就白做了**。
   返回值里带 `judgment_policy` 明说"不得改写或弱化"。
2. **工具出口统一过输出契约**：`_guard_payload()` 复用 `constraints.scrub`，
   把客户端没提过的药食名按类别概化。新入口绝不能成为泄漏守卫的绕道。
   *反直觉的一步*：守卫只回传"是否概化过 + 计数"，**不回传被替换掉的名字**——
   否则守卫自己又成了一条泄漏渠道。
3. **内部话术不进返回值，也不进 `description`**：`description` 是对外可见的
   （会进客户端模型的上下文），贴规则库原文等于把规则公开。
4. **只读**：阶段 1 不暴露任何写工具（不调 `update_from_message` / `record_herbs` /
   `append_timeline` / `record_safety_hits`）。已加常驻断言：调用全部工具前后
   SQLite 状态与 `chat.db` 的大小/修改时间必须**一字不变**。
5. **stdio 下日志一律走 stderr**：stdout 是 JSON-RPC 协议流，一个 `print` 就污染它，
   客户端报的是"JSON 解析错误"——现象离原因很远。本项目统一用 `app/mcp/_boot.py::log()`。

### 三个实测发现（都是照文档写不出来的）

**① `cwd` 这条路走不通 —— 而且光靠"自己 chdir"还不够**
chroma 开库必须走相对路径，所以进程工作目录要是项目根；而 MCP 是宿主按配置拉起子进程的，
启动目录由宿主决定。实测 WorkBuddy 的 `mcpServers` **没有 `cwd` 字段**
（只有 `command/args/env/runtime/staticEnv`）。

但更关键的是：`python -m app.mcp` 要能 import 到 `app` 包，靠的是 `sys.path`——
**这件事发生在 `_boot` 自 chdir 之前**。所以正确的写法是两件事各有着落：

```jsonc
{
  "mcpServers": {
    "tcm-kb": {
      "command": "D:/Anaconda/envs/rag-agent/python.exe",
      "args": ["-m", "app.mcp"],
      "env": {
        "PYTHONPATH": "<项目根>",        // ← 让 import 找得到 app 包
        "PYTHONIOENCODING": "utf-8"
      }
    }
  }
}
```

`PYTHONPATH` 负责"找得到"，`_boot.ensure_project_root()` 负责"工作目录对"。
回归里为此加了**负对照**：cwd 错且无 `PYTHONPATH` 时必须起不来（否则说明前提不成立）。

**② 宿主配置里不需要写任何 API Key**
`app/llm.py` / `embed.py` / `rerank.py` 都用**绝对路径** `load_dotenv(BASE_DIR / ".env")`，
不依赖 cwd。所以服务自己就读到 Key —— 配置里（以及将来可能进 git 的配置文件里）
**没有明文密钥**。这条也有常驻断言：用剔除掉两个 Key 的 env 起服务，`tcm_search` 仍成功。

**③ SDK 2.x 把 `FastMCP` 改名成 `MCPServer`**
`from mcp.server.fastmcp import FastMCP` 在 mcp 2.2 会直接抛
`ModuleNotFoundError`（并提示改名）。正确写法是
`from mcp.server.mcpserver import MCPServer`；`run(transport)` 支持
`stdio` / `sse` / `streamable-http`。网上绝大多数教程还是 v1 写法，照抄必挂。

### ★ 缺状态输入不得静默给宽松档（2026-09-17 部署校验挖出）

**现象**：写校验脚本时参数名写成 `states`（真名是 `states_text`），**没有报错**，
但因为状态没传进去，`当归` 被判成 **「可执行」**。

**根因**：pydantic 对多余字段默认 `extra="ignore"`（**静默丢弃**），
而 `states_text` 当时有默认值 `""` —— 于是"漏传"与"确认没有状态"变成了同一件事。
**安全判读最坏的失败模式就是漏报禁忌，而"缺输入 → 给最宽松档"恰好制造了它。**

三层加固（每层都有常驻断言）：

| 层 | 做法 | 效果 |
| --- | --- | --- |
| 契约 | `states_text` **去掉默认值改必填**；没有状态就**显式传空串** | 漏传 = 参数校验失败（**响亮报错**）；"我忘了传"与"我确认他没提"在契约上分开 |
| 回显 | 返回值加 `input_received`，回显实际收到的 `items` / `states_text` | 参数写错时一眼看出"我传的没进来"，而不是拿到偏松档位毫无察觉 |
| 自曝 | 状态为空时 `confidence=low` + `caveat` 明说"未考虑孕期/哺乳/在服西药/慢病，**不要当作可以放心使用的依据**" | 结论不隐藏自己的边界 |

通用教训：**函数签名就是接口契约，模型只读 schema 不读源码**——
参数名与必填性要**按"会被误用"来设计**，不是按"我知道怎么调"。

### ★ 没有结论的条目不得消失（2026-09-17 首次真实客户端往返挖出）

**现象**：真实提问「孕妇能不能喝当归鸡汤」，返回的 `items` 里只有当归与群体级提示 ——
「**鸡肉**」一条规则都没命中，于是它**从结果里彻底消失了**。调用方只能去 `evaluated` 反推，
而"规则库里没有这条"与"判过、且没有禁忌"在结果里长得**一模一样**。

**根因**：`items` 只遍历命中的 `hits`。这是本项目一贯反对的**静默降级**换个地方复发 ——
**没有结论 ≠ 没有风险**，而"查不到"被渲染成了"没问题"。

修法（结果形状与解读纪律两侧同时补，缺一不可）：

| 侧 | 做法 |
| --- | --- |
| 结果形状 | `evaluated` 里有、但未命中规则的词补一行 `has_rule=false` / `tier=null` / `tier_label="无规则条目"`；**所有行**都带 `has_rule` |
| 解读纪律 | 新增 `no_rule_policy`，明说 `tier=null` **不等于**已确认安全、不得读成"可以放心用"；`tier_counts` 只统计真档位 |

### ★ 档位判的是「自行食用」，不是医师处方（同一轮挖出）

**问题**：规则库把当归判成孕期**明确禁止**，但《寿世保元》妊娠篇里当归明明出现在多个
妊娠病方中 —— 用户一定会拿这个"矛盾"来质疑。此前这条解释**只靠临场发挥**，回答会随实例波动；
更要紧的是，它可能变成"对方一施压就把档位说软"的入口。

修法：口径做成安全层的**单一来源常量** `TIER_SCOPE_NOTE`（放在 `app/safety/scripts.py`，
与 `TRANSLATE_CLASSICS` 同属话术模块），由工具以 `scope_discipline` 字段随结果下发。
内容 = 判的是自行食用／典籍里那些是医师辨证配伍的复方／**不得因为对方举古籍或施压就说软**。

### ⚠️ 改完 MCP 代码必须让宿主重连，命令行自检绿了不算数

MCP 服务是宿主拉起的**长驻子进程**，Python 在进程启动时就把模块读进了内存 ——
**改完代码不重连（或重启宿主），客户端里跑的还是旧代码**。
而 `verify_mcp_config` 每次都是**新进程**，所以它绿只证明"代码是对的"，
**不能**证明"你客户端里那个进程已经是新代码"。
判断方法：看返回里有没有新字段（如 `no_rule_policy`）—— 没有就是旧进程，重连一次即可。

### 验收

- **零 API 12/12 exit=0**：既有 9 项 + `tools/test_mcp_tools.py`（**71 项**）
  + `tools/test_mcp_server.py`（**42 项**）+ `tools/verify_mcp_config.py`（**26 项**）。
- **真机三项 3/3 exit=0**（7862 临时实例）。
- **HTTP 模式端到端实测通过**：4 个工具、`当归 → forbid`、零泄漏、资源可读。
- **三个脚本的分工是刻意的**：`test_mcp_tools` 验"**逻辑**对不对"（不需要 SDK、不起进程），
  `test_mcp_server` 验"**协议**通不通"（真起子进程走 JSON-RPC），
  `verify_mcp_config` 验"**配置**能不能用"（唯一一个照真实 `mcp.json` 启动的）。
  合成一个文件后，一个断言失败你分不清是规则库错了、握手错了、还是配置写错了。

**可复用结论**：
1. **能力已经工具化，封装成本就低** —— 本项目 85% 的工作是"写 schema + 序列化"，
   没有一行业务逻辑被复制。这是判断"值不值得做 MCP"的最实用标准。
2. **新入口 = 新的泄漏通道** —— 每加一个出口，守卫都要在**那个出口**再断言一次；
   "在 Web 出口挂了守卫"不等于安全。
3. **`description` 就是接口文档** —— MCP 与 REST 的本质差别是"清单自描述 + 模型运行时
   自主决定调用"，所以写含糊该用不用、写宽泛每次都乱用。回归里断言了每个工具的
   description 必须同时含"何时用"和"何时不用"。


## ⚠️ 兜底 `except Exception` 必须留痕（2026-09-16 静默故障实录）

**现象**：改动后跑 `tools/e2e_safety_check.py`，三轮对话**一个 `safety` 事件都没有**、
追问清单也没有，而四个纯规则单测**全绿**。

**根因**：给接诊层加"按会话隔离"时，`intake.screening_keys()` **漏声明了 `conv_id` 形参**
（但函数体里的回退分支却已经在用它）。三处调用点全部 `TypeError`：

```
app/rag.py::_safety_guard        ─┐
app/agent/agent.py::_prescan      ├─► 都被各自的 try/except Exception 静默吞掉
app/multiagent/nodes.py::_build_intake ─┘
```

于是"安全事件 + 追问清单"**整条链路凭空消失**，退化成一个没有护栏的回答——
而单测不经过这三个函数，自然全绿。

**修法**：① 补形参；② 三处兜底全部 `print(traceback)` 到 stderr。**降级可以，但不能无声**——
一个静默的兜底等于把"功能没生效"伪装成"这次没有风险"。

**两条通用教训**：
1. **签名改动必须跑打真服务的端到端脚本**。"单元自检验图结构、规则单测验扫描层，两头都对不代表串起来对"——
   这个项目第 N 次验证这句话。
2. **凡是 `except Exception: return 空`，都要问一句"如果它天天在触发，我怎么知道？"** 答不上来就该加日志。

**顺带修掉的同类窄口缺陷**：`scan._TAKING` 有"正在吃 / 在服用"却漏了口语最常用的「**在吃**」——
「有高血压**在吃**氨氯地平」被判定 `taking=False`，话术从"请暂停并咨询"降级为"是否适合你"，
而附子同句也被连带判 False。已补，并加反向守卫（「朋友推荐我吃阿胶」仍为 False，不因新词误判）。

**同一轮还修掉的假通过**：`tools/test_fresh_session.py` 旧版把档案写到**无会话作用域**
（`PUT /api/profile` 不带 `conv_id`），然后在新会话里聊天——两者作用域不同，会话根本读不到那份档案，
场景 B 的"✅ 通过"其实一直在验空档案。现已重写为**会话作用域版**：档案写进测试自己的会话、
删会话即完全还原，且断言场景 B 的档案提醒**必须存在**（实测 `origin=profile` 命中 1 项、本轮 0 项）。

## ⚠️ PDF 文本层的「部首码位」污染（评估体系挖出来的静默缺陷）

**现象**：在语料里搜 `人参`、`大枣`、`独取寸口`，一个都搜不到；但 `上品`、`延年` 却能命中——不是内容缺失，是**字符本身错了**。

**根因**：部分中文 PDF 的字体缺标准 Unicode 编码表，文本层提取时把字形映射到了 Unicode 的「部首区」而不是「汉字区」：

| 语料里实际存的 | 码位 | 应该是 | 码位 |
| --- | --- | --- | --- |
| `⼈` | U+2F08 KANGXI RADICAL MAN | `人` | U+4EBA |
| `⽓` | U+2F53 KANGXI RADICAL STEAM | `气` | U+6C14 |
| `⻝` | U+2EDD CJK RADICAL EAT ONE | `食` | U+98DF |
| `⻩` | U+2EE9 CJK RADICAL SIMPLIFIED YELLOW | `黄` | U+9EC4 |

**影响面**（实测）：**880 / 2597 块（33.9%）被污染，183 种字符、51260 次出现，且 5 本 PDF 是 100% 全中**；`.md`/`.txt` 一丝不染。

| 文件 | 污染块 / 总块 |
| --- | --- |
| 《神农本草经》.pdf | 278 / 278 ⚠️ |
| 《黄帝内经·灵枢》.pdf | 245 / 245 ⚠️ |
| 《饮膳正要》.pdf | 158 / 158 ⚠️ |
| 《食疗本草》.pdf | 143 / 143 ⚠️ |
| 《难经》.pdf | 56 / 56 ⚠️ |
| 其余 4 份 | 0 ✅ |

**为什么必须修**：① 关键词/字符串召回直接漏；② `⼈` 在 bge-m3 词表里是罕见 token，向量与"人"相距很远，这批书几乎召不回来；③ LLM 读到 `⽯⻙ 味苦平，主劳热邪⽓` 这种字形，误读与幻觉概率显著上升。

**为什么叫"静默"**：终端和浏览器里部首字形与正字几乎一样，肉眼逐页看发现不了；只有量化评估的关键词覆盖率异常为 0 才暴露它。

**修法**（`app/textfix.py`，入库前统一调用，幂等）：
- **康熙部首块** U+2F00–U+2FD5 自带 NFKC 兼容分解 → `unicodedata.normalize("NFKC", …)` 自动还原；
- **CJK 部首补充块** U+2E80–U+2EFF **没有**兼容分解（实测 `⻝` 归一化后还是 `⻝`）→ 35 个字符手工建表映射；
- 只归一"兼容/部首区"，不跑全局 NFKC（避免把全角 ASCII、罗马数字等一并改写）；
- `find_artifacts()` 可做"入库后污染残留应为 0"的自检断言。

> 通用经验：**PDF 语料入库前一定要做 Unicode 归一化 + 污染体检**。这不是本项目的特例，中文 PDF 文本层提取普遍有这个风险。

## 量化评估体系（`python -m app.eval`）

没有评估之前，所有优化都只是"看起来更好"。上面那个污染 bug 就是靠指标异常发现的——**评估是唯一能抓出"静默失效"的手段**。

```bash
python -m app.eval --validate      # 只校验测试集与语料是否对得上（零 LLM，先跑这个）
python -m app.eval --retrieval     # 仅检索指标（含自反思对照）
python -m app.eval --full          # 四项全跑，出 JSON + Markdown 报告
```

| 指标 | 回答什么问题 | 判分口径 |
| --- | --- | --- |
| recall@1 / 书级 recall@4 / MRR | 命中哪本书 | gold 来源出现在 top-k |
| **金标块召回 kw_hit@4** | 这个块真的召回对了吗 | 半数以上标注词落在 top-4（书级粒度太粗，这条才是主指标） |
| 关键词覆盖率 | 召得全不全 | 标注词在 top-4 正文+元数据中的出现比例 |
| 答案忠实度 | 有没有幻觉 | LLM-as-judge：每条实质论断是否都能在参考资料溯源 |
| 拒答正确率 | 该拒不该拒 | 域外期望拒答；域内**误拒同样算失败** |
| 长期记忆保持率 | 第 1 轮说过的话第 9 轮还记得吗 | 同会话 9 轮后追问 + 新建会话追问 |

两个关键设计：
- **自反思检索的净增益用对照实验量化**：同一测试集分别以「关闭自反思」和「开启自反思」跑两遍，差值 Δ 就是方向二的价值。没有这个对照，"我做了自反思"只是个说法不是数据。
- **`--validate` 先跑**：标注写错是评估失真的最大来源（gold 来源不在库里、关键词压根不存在），先校验再评估。

## 评估驱动的修复闭环（测 → 改 → 复测）

评估的价值不在出报告，而在于逼出下面这些"不测就永远看不见"的问题：

| # | 评估发现的问题 | 修法 | 复测 |
| --- | --- | --- | --- |
| 1 | 语料 34% 的块被 Unicode 部首污染（见上节） | `app/textfix.py` 入库前归一 | 污染 51260 → 0；石韦/人参/黄精 0% → 100% |
| 2 | 问"写个 Python 快排"模型直接输出代码，没遵守"资料库没有就坦诚说没有" | `ANSWER_SYSTEM` 加规则 4（明显非养生科普的问题直接说没有） | 域外拒答 4/5 → **5/5** |
| 3 | 用自身知识**补写《抱朴子》《黄帝内经》引文**（judge 判"参考资料中未出现此引文"） | 加规则 5：每处引用必须能在参考资料里**逐字找到** | 引文均为上下文实有内容 |
| 4 | 跨会话记忆**召回不稳定**：同一句问法有时记得"长期熬夜"有时不记得 | `memory.py`：条目 ≤30 时**全量注入**，不做 top-k 截断（小集合按相似度截纯属引入抖动，30×30 字 ≈ 600 字，成本可忽略） | 跨会话回忆稳定通过 |
| 5 | 问"我平时作息怎么样"，模型先说"资料库中没有你个人作息记录"——把【用户背景】当成了资料库 | 提示词明确：【用户背景】里的内容**不属于**"资料库中没有" | 个人化问题直接用记忆回答 |
| 6 | 评估器自己有 bug：记忆探针用死关键词判通过，模型把"程序员"复述成"常年坐办公室"就被误判失忆 | 改成**同义组匹配**，并剔除"作息"这种问句里就有、会假命中的词 | 探针判定与人工判断一致 |

> 表里第 6 条值得单独说：**评估器本身也要被评估**。判定口径写得太死，会把"答对了但换个说法"误判成失败，然后你会去修一个根本不存在的问题。

## Web 界面（`python -m app.server`）

| 页面 | 地址 | 特点 |
| --- | --- | --- |
| 养生问答 | `/` | DeepSeek 风格：多会话 / 置顶 / 重命名 / SSE 流式；**实时显示自反思检索过程与三层记忆状态** |

关键实现：
- SSE 用 `fetch` + `ReadableStream` 手动解析（浏览器 `EventSource` 只支持 GET，无法带 POST body）；
- 用户消息先落库再生成：即使生成中途断网，历史也完整；
- `RAGSession` 现在直接从 SQLite 读记忆，无需缓存会话对象（早期版本缓存 `_sessions` 会与库不同步）；
- 并发护栏 `_chat_lock`：同一时刻只放行一个聊天请求，避免多线程同时写 SQLite/chroma；
  **但锁绝不能跨 SSE 流持有**，见下面「SSE 死锁事故」。

其余接口：`GET /api/profile`（长期档案）、`GET /api/memories`（长期记忆）、`GET /api/agent/{id}/state`（问诊状态）。

启动参数：`--host`（默认 `127.0.0.1`，只监听本机）、`--port`（默认 7860）。
启动前先做端口预检，被占时直接打印「换端口 / 查占用 PID / 结束进程」三条命令并退出，
不再把 uvicorn 的 `Errno 10048` 原样抛给使用者。

> 约定：服务由使用者在自己终端里前台启动（日志可见、Ctrl+C 即停）。
> 不要用后台常驻方式占着 7860——它不会自己退出，下次启动必撞端口。

## ⚠️ SSE 死锁事故：锁不能跨流式响应持有（2026-09-14 实测复现）

**现象**：一切正常跑了一段时间后，所有聊天请求全部无响应——页面一直转圈，
但 uvicorn 访问日志仍在刷 `POST /api/conversations/{id}/chat 200 OK`，重启才恢复。

**根因**（三个条件同时满足才会发生）：

| 条件 | 说明 |
| --- | --- |
| ① 同步端点 + 同步生成器 | `def api_chat()` 里 `with _chat_lock: for event in sess.ask_stream(...): yield ...`，锁横跨整个流 |
| ② 客户端中途断开 | 关页面 / 刷新 / curl 被 `head -c` 截断 / 请求超时 |
| ③ Starlette 迭代被取消 | 它用 `anyio.to_thread.run_sync` 迭代同步生成器，**取消的是等待方，杀不掉工作线程**：生成器被永久挂在 `yield` 上，`with` 的 `__exit__` 永不执行 |

一旦 ①②③ 齐备，锁就**永不释放**，之后每一个聊天请求都卡在获取锁——服务被焊死。

**最准的判据**：`/` 还能打开、`200 OK` 还在刷，但 `store/chat.db` 里**一条 assistant 消息都没有**
（`storage.add_message` 在 `with` 块之后，永远执行不到）。别被 200 骗了。

**修法（把「干活」与「推流」解耦）**：

| 角色 | 职责 |
| --- | --- |
| 生产者 | 独立**守护线程**持锁跑完整个 RAG 流程，事件塞进 `queue.Queue`；线程不受客户端影响，一定会跑到底 → **锁一定释放** |
| 消费者 | SSE 生成器只从队列取事件推给前端；客户端断开只是没人取了，生产者照常收尾 |
| 兜底 | `Queue.get(timeout=180)`，生产者线程意外死亡也不会让前端干等 |

**通用经验**：任何「跨 `yield` 持有的资源」都不能依赖客户端的正常关闭来释放。
流式接口里，`try/finally` 和 `with` 都是**不可靠**的——它们只在生成器被 `close()` 时执行，
而连接中断时没人保证会调用 `close()`。要释放，就把生命周期挪到独立线程/任务里。

回归测试：先发一个请求并在 2 秒后掐掉客户端，紧接着再发一个——修复前必卡死，修复后正常返回。

## ⚠️ chromadb 1.5.9 / Windows 四条铁律（踩坑实录，全部实测复现）

1. **先算向量再写库**：langchain-chroma 的 `add_texts` 会边算 embedding 边写库（写入期发起 HTTP 请求），干扰 chromadb 后台 HNSW 落盘线程——向量进了 sqlite 但索引 bin 文件从未落盘，跨进程查询必报 `Error loading hnsw index`。→ `index.py` 两阶段写入：先一次性算完全部向量，再零网络请求单批 upsert。
2. **不要在 Python 里 rmtree 删库目录**：批量删除可能被安全机制中止，留下半删除残缺目录（表现同样是 hnsw 加载错误）。→ 重建用 `delete_collection()` 逻辑删除；目录级删除只在命令行手动执行。
3. **单批 upsert**：多批小写入会触发 compaction，Windows 上有丢索引风险；千级规模单批直写实测稳定。
4. **打开库必须用相对路径**：chromadb 1.5.9 的 Rust 层无法从**含中文等非 ASCII 字符的绝对路径**加载 HNSW 索引（建库写入不受影响，但查询必炸）；相对路径由 Rust 按进程工作目录解析，不受影响。→ 所有打开库的地方统一走 `app.paths.chroma_store_path()`，**不要**直接传 `str(STORE_DIR)`。

## ⚠️ langchain-openai 接第三方 embedding 的坑

`OpenAIEmbeddings` 默认 `check_embedding_ctx_length=True`，会先用 tiktoken 把文本切成 **token ID 数组**发给 API。OpenAI 官方端点能正确处理，但 SiliconFlow 不能——返回的向量与直接发字符串**完全不同**（实测同一文本余弦仅 0.31），表现为"召回全乱"：明明库里有的内容排到 300 名开外。→ `app/embed.py` 已设 `check_embedding_ctx_length=False`。

**通用结论**：「OpenAI 兼容端点」只保证协议兼容，不保证行为兼容。接第三方平台时一定要做「裸调 API vs SDK 封装」的一致性对照。

| 追问答非所问 | 正常已被"问题改写"解决；看 `ask.py` 输出的"改写后问题"是否符合预期 |
| 问诊卡在第一题 | 检查工具描述里的"开始/重来"是否分离、`begin_consultation` 是否只对 IDLE 可见 |
| OCR 太慢 | 用 `--no-ocr` 跳过；或调低 `app/ocr.py` 的 `DEFAULT_DPI`；中断后重跑会自动续跑 |
| OCR 结果只有前几页 | 检查缓存键是否含页数范围（调试残留缓存会污染正式结果） |
| 建库日志被 `fontTools is required...` 刷屏 | 缺 `fonttools`，`pip install fonttools`；噪声本身已由 `configure_pdf_logging()` 静默，`--verbose` 可恢复 |
| 每次都全量重跑、几小时 | 检查 `store/ingest_manifest.json` 是否被删；要对不上就 `--rebuild` 一次，之后即增量 |
| `UnicodeDecodeError: byte 0x..` | 编码不在 5 种候选内；用 `file -i` 或十六进制 dump 确认后加入 `_read_text_smart` 的候选列表 |
| 端口 10048（7860 被占） | 多半是上一次的服务进程没退干净（后台起的服务不会自己走）。查占用者：`netstat -ano \| findstr :7860` → 最后一列即 PID → `taskkill /F /PID <pid>`；或直接换端口 `python -m app.server --port 7861`。启动时已做预检，会把这两条命令直接打给你 |
| 语料里明明有这个词却搜不到 | 大概率是 PDF 文本层的「部首码位」污染（`⼈`≠`人`）；跑 `python -m app.eval --validate` 看残留数，重建库即可 |
| 页面一直转圈但日志刷 200 OK | 踩了 SSE 死锁（见上文）：查 `store/chat.db` 有没有 assistant 消息；修复后仍卡则重启服务 |
| 想查源码 | `_ref/langchain`、`_ref/langgraph` 是源码字典，grep 定位即可 |
